---
title: 'Plan your repository layout'
description: 'Set up a root, forge directories, and namespace paths that keep every local checkout predictable.'
---

forgemap manages a local tree whose paths identify a repository by forge,
namespace, and repository name. Pick the root directory once, then let each
forge use its own directory beneath it. A checkout therefore has the shape
`<root>/<forge directory>/<namespace…>/<repository>`.

## Start with a root

The root is the boundary of the collection. Point forgemap at an existing
directory when adopting a collection, or choose an empty directory before the
first clone. The project README owns the install command and starter-config
example; use `forgemap config init` when the collection needs a new config.

## Keep forge names separate from paths

A forge's configured name selects it in a slug, while its directory determines
where its repositories live on disk. Keeping those two ideas separate lets a
local directory name reflect the host without making every command spell that
host. A bare slug uses the configured default forge; qualify a slug when a
different forge owns it.

## Let namespaces match the forge

The final path segment is always the repository. The preceding segments are its
namespace: one owner on GitHub, and nested groups where the forge supports
them. forgemap stops its scan at the first `.git` entry, including a `.git`
file used by worktrees and submodules, so a repository is never mistaken for a
directory containing more repositories.

The layout validator is the preflight check for this contract. Run it after
configuring a forge or importing an existing tree, before relying on commands
that search the collection.
