---
title: 'Configure a forge'
description: 'Describe where a forge belongs locally so forgemap can resolve slugs and clone paths consistently.'
---

A forge configuration connects a name used in commands to a host and the
directory below the collection root. Start from the generated config instead
of copying a partial object: it keeps the configuration in the format the CLI
loads and validates.

## Choose the adapter deliberately

Use the adapter that matches the remote's capabilities. GitHub and GitLab
integrations use their respective command-line clients for forge-aware work;
the generic Git adapter is the appropriate choice for a plain remote or a
GitLab-shaped host without the GitLab client. The adapter choice also defines
which namespace depths forgemap accepts.

## Set the host and directory together

The host lets forgemap recognize URLs and SSH-style slugs. The directory is the
local segment directly below the root. Together they make a clone target
deterministic without requiring a command to know a full filesystem path.

::callout{title="Validate before cloning"}
Run `forgemap validate` after changing a configuration. It checks the resolved
config, the collection root, and the tools required by the configured adapters.
::

## Keep configuration discoverable

forgemap searches upward from the current directory before using the global
fallback. That makes the same configuration available while working inside one
of its checkouts. When a command must use another config, select it explicitly
instead of depending on the current directory.

For the starter file, supported keys, and command-specific overrides, use the
[configuration reference in the README](https://github.com/TitusKirch/forgemap#%EF%B8%8F-configuration).
